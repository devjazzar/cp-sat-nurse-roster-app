## 2. Security posture

The application's core access model held up. No path was found by which an anonymous visitor reaches data, or by which a nurse or unit manager reaches another unit's rosters, leave or attributes through the normal scoped routes. A System Admin is refused on every roster, attribute and leave route; the one way round that this audit confirmed is the backup finding below, where a session taken from a downloaded backup lets its holder act as another user. Authentication is on by default for every route, unit scope is enforced in one place, and there is no injection sink fed by user input.

What the audit did confirm are five low-severity issues, each reproduced with dummy data in the sandbox: a backup file that carries live session rows; two narrow information or access leaks across the unit boundary (a cover-offer refusal that names other units' nurses, and a former manager's lingering read of a unit's approved roster); and two ways a signed-in nurse can impose cost or nuisance on others (a far-future month that multiplies database queries, and unlimited swap propose/withdraw rounds that flood a chosen colleague's notification list).

Seven further leads are source-grounded but could not be settled without a browser, a real proxy, a real solver or deployment facts. Most concern availability: nothing limits requests per client anywhere in the repository (login hashing, login rows, slow request bodies, push subscriptions, the solve queue), and no response carries a frame-blocking header. They carry no severity until validated.

### 1. A far-future month makes one request run a database query per nurse per month in between, for any signed-in nurse and, on a solve start, under the hospital-wide catalogue lock

- **Severity:** low (likelihood medium, impact low); confidence high
- **Fingerprint:** `backend/closes/chain.py:Chain.carry_in:per-nurse-per-month-queries-up-to-caller-chosen-month`
- **Source location:** entry `backend/requesting/preferences_api.py:84`, sink `backend/closes/chain.py:135`
- **Lower-trust principal:** A signed-in Staff Nurse or Unit Manager of the hospital sending ordinary API requests with a month far in the future.

Several routes take a month from the caller and work out each nurse's carry-over into it. The carry-over chain walks month by month from the nurse's latest closed month (or first approved roster) to the requested month, and each step reads her placements and looks up an approved roster. The month is only limited to the years 1925 to 2076, so once anything has closed, a request for 2076-12 costs about 600 steps per nurse instead of one or two. Observed in the sandbox with one closed month (2026-09): a Staff Nurse's GET /api/preferences/mine?month=2076-12 ran 1,219 statements (19 for 2026-12); a Unit Manager's GET /api/units/{id}/solves/preview?month=2076-12 ran 1,836 statements for a 2-nurse unit and 3,048 for a 4-nurse unit (36 and 48 for 2026-12), which fits (nurses + 1) x months ahead; GET /api/units/{id}/close?month=2076-12 ran 3,027. POST /api/units/{id}/solves for 2076-12 with a solve of that month already queued ran the same 3,048 statements, answered 409 and created nothing, and while it ran a second database connection could not lock the hospital settings row, which solve starts of every unit, month closes, approvals and catalogue changes take first. Each request runs in one of three synchronous web workers. Not measured: a unit of realistic size (about 18,700 statements for 30 nurses by the same arithmetic), production query latency, and any effect of several such requests at once; no load was generated.

**Root cause.** Chain.carry_in loops over every month up to a caller-chosen target, and each step issues an uncached placements query for the nurse (membership.placement_in) and an approved-roster lookup, although months after the last approved roster change nothing but the year reset. The routes that reach it accept any month up to December 2076 and, on the solve routes, assemble the month before checking the cheap refusals; start_solve does so while holding the hospital settings and unit rows FOR UPDATE.

**Intended behaviour.** A request for a caller-chosen month should cost database work that does not grow with how far ahead the month is, and a solve start that is going to be refused should not hold the hospital-wide lock for longer than a refusal takes.

**Conditions.**
- _authentication_level_: A signed-in account. A Staff Nurse reaches the walk for her own chain (about two queries a month ahead); a Unit Manager reaches it for every nurse of their own unit, and only a Unit Manager reaches the path that holds the hospital settings lock.
- _data_state_: The nurse has a closed month or an approved roster that holds her. The schedule closes each month on its own, so an installation in use meets this after its first month; before that the walk does not run.
- _system_configuration_: The shipped deployment: three synchronous gunicorn workers, no request rate limit in the Caddyfile, no database statement or lock timeout.

**Bounded local reproduction (sandbox, dummy data).**
1. In a throwaway database, create two dummy units of 2 and 4 staff nurses with their managers, and one closed month (a MonthClose for 2026-09 with a closed CarryOver for each nurse).
2. Signed in as each principal through /api/auth/login, send each request once for month 2026-12 and once for 2076-12, counting the SQL statements of the request with a connection execute wrapper.
3. For the POST, first create a queued Solve row for the same unit and month, and during the request try SELECT ... FOR UPDATE NOWAIT on the hospital settings row from a second connection.
4. Compare the statement counts; send nothing concurrently and do not repeat requests.

**Observed result.** Sandbox run of harness-carry-walk.py (PostgreSQL 18, one CPU, date 2026-11-10), output in check-carry-walk.txt. Staff Nurse GET /api/preferences/mine: 19 statements for 2026-12, 1,219 for 2076-12 (605 placement reads, 603 roster reads, 1.0 s). Manager GET solves/preview, 2-nurse unit: 36, 72 and 1,836 statements for 2026-12, 2027-12 and 2076-12; 4-nurse unit: 48, 108 and 3,048 (2,414 placement reads, 2.4 s). Control with nothing closed: 43 statements for 2076-12. Manager POST solves for 2076-12 with a queued solve of that month: 409 'A solve of this month is already queued or running.', 3,048 statements, 2.6 s, Solve rows 1 before and 1 after; the hospital settings FOR UPDATE was statement 3, before any placement read, and the second connection's FOR UPDATE NOWAIT on that row failed with 'could not obtain lock on row in relation "hospital_hospitalsettings"' during the request and succeeded after it. Manager GET close?month=2076-12: 3,027 statements. The seconds are the sandbox's and say nothing about the deployed stack.

**Impact.** Availability only, and it ends when the requests stop: each request occupies one of three web workers for the length of the walk (about 1 s for a nurse and 2.5 s for a 4-nurse unit in the sandbox), and a refused solve start holds the hospital settings lock for that time. Lasting harm to other users needs a sustained stream of such requests, which was not generated or measured; no data is read or changed.

**Priority rationale.** One ordinary GET by any signed-in Staff Nurse triggers it, the data state is the normal one after the first month, and nothing limits the month or the request rate; it does need a signed-in member of the hospital acting on purpose, since the application's own pages ask for near months.

**Smallest source fix.** Make the walk's cost independent of the requested month, then bound the month. (1) In Chain.carry_in, stop stepping once no approved roster lies between the current step and the requested month: from there each month only hands on what came into it with no shift history, so the result is carried.into(month before the target) | NO_HISTORY in one step; look the last approved roster month up once per chain. (2) Read a nurse's placements once per chain (or prefetch them in assemble) instead of once per month. (3) Refuse a month more than a small number of months past the hospital's current one in the routes that take a month (solve and re-plan preview and start, close view, My month, My preferences). (4) In start_solve, check the refusals that need no assembly (month over, frozen roster, a solve already queued or running) before assemble, so a refused start releases the hospital settings lock at once. The code below is a sketch of (1) that was not run against the test suite.

### 2. Offering a cover names nurses of other units to a unit manager

- **Severity:** low (likelihood low, impact low); confidence high
- **Fingerprint:** `backend/covers/steps.py:offer:unscoped-nurse-name-in-refusal`
- **Source location:** entry `backend/covers/api.py:179`, sink `backend/hospital/api.py:25`
- **Lower-trust principal:** A signed-in Unit Manager of one unit, using the application's own API with their own session, who wants the names of nurses in units they do not manage.

A unit manager offers a cover by posting a list of hospital IDs. Every ID that is not in the list of nurses who could take the cover is refused with a sentence that begins with that person's full name. The name is looked up among every nurse profile in the hospital, not among the people on the cover's own roster, so the ID of a nurse placed only in another unit comes back as that nurse's full name, while an ID with no nurse profile comes back unchanged. A manager can send up to 500 IDs in one request and learns, for each, whether a nurse profile exists and whose it is. This was observed locally with two dummy units: the manager of unit A received the full name of a nurse placed only in unit B. The lookup has no role filter either, so by source the same holds for another unit's manager who has a nurse profile; that case was not run. What is disclosed is a name and the fact of a profile. Nothing of the roster, leave, attributes or credentials is disclosed and nothing is written.

**Root cause.** In backend/covers/steps.py, offer() builds its name table with NurseProfile.objects.select_related("user").filter(user__username__in=added) (lines 95-96), which has no unit or roster filter, and then puts name_of(nurses[hospital_id].user) into the refusal for every submitted ID that is not in the judged list (lines 97-100). The judged list is scoped to the cover's roster; the lookup used to word the refusal is not.

**Intended behaviour.** A unit manager reads only the nurses of their own unit: docs/ARCHITECTURE.md line 101 gives a manager 'Read nurses' for their own unit only, and line 127 says a unit manager sees nothing of other units. The rest of the code keeps to this and treats another unit's nurse the same as no such nurse: the manager's nurse list is membership.on_the_list_of(unit) (backend/nurses/api.py:193-201), a pin edit says only the ID back (backend/rosters/editing.py:54-56), recording leave answers the same 403 whether another unit's nurse exists or not (backend/nurses/leave_api.py:210-215), and a swap echoes an ID that is not on the roster (backend/swaps/judging.py:100-102). No route was found that gives a manager the names of nurses who were never on their unit's list or rosters. A hospital ID that is not on the cover's roster should therefore be refused without being resolved to a name.

**Conditions.**
- _authorization_role_: The caller is signed in as a Unit Manager who holds a unit.
- _data_state_: The manager's unit has a cover that is open or offered. A manager can open one by hand for any shift-day today or later of a month whose roster is approved (POST /api/units/{unit_id}/covers); the local run did so.
- _data_state_: The cover's roster can be checked and its shift-day is below its maximum headcount. Otherwise the offer answers 409 before the lookup (backend/covers/steps.py lines 91-93).
- _data_state_: The manager supplies hospital IDs that exist, in their exact case. They must be known or guessed, for example from a staff-number pattern, up to 500 in one request.

**Bounded local reproduction (sandbox, dummy data).**
1. Run harness-offer.py in the database sandbox (one run, throwaway PostgreSQL 18, no network, config.test_settings, repository at commit f2492e0 mounted read-only and unchanged). It uses dummy data only.
2. The harness seeds two units, each with its own manager. Unit A holds the solver's four-nurse sample and an approved roster of the current month written as rows; one more staff nurse, 'Zeta Otherunit' with hospital ID sa-b-0001, is placed only in unit B.
3. It signs in as unit A's manager through POST /api/auth/login and opens a cover by hand through POST /api/units/{A}/covers for Day on the month's last day. The hospital's clock is not changed.
4. As a control it reads GET /api/nurses (the manager's own list) and GET /api/units/{B}/covers (another unit's page).
5. It sends the one offer: POST /api/units/{A}/covers/{cover}/offer with {"nurses": ["sa-b-0001", "sa-nobody-9999"], "note": ""}, writes the status and body to check-offer.txt and stops.
6. The harness holds a second scene (June 2026 with the clock moved, as the test suite does) only as a fallback. It did not run.

**Observed result.** Executed locally once, on 2026-11-10 (check-offer.txt). The cover opened with 201 and its check listed only unit A's four nurses. The manager's own nurse list held unit A's four nurses and not 'Zeta Otherunit'; GET /api/units/{B}/covers answered 403. The offer answered HTTP 422 with two messages: 'Zeta Otherunit cannot take this cover now, so it cannot be offered to them.' and 'sa-nobody-9999 cannot take this cover now, so it cannot be offered to them.'. The full name of unit B's nurse was returned to unit A's manager in place of the ID sent, and the unknown ID was echoed, so the two cases can be told apart. No offer row was written, the cover stayed open and no cover.offered audit entry was made.

**Impact.** It discloses the full name behind a hospital ID, and whether a nurse profile exists, for staff of other units in the same hospital. No roster, leave, attribute or credential is exposed and nothing is changed.

**Priority rationale.** It needs a Unit Manager account, a waiting cover in that manager's unit (which the manager can open by hand once a roster of the current or a later month is approved), and hospital IDs that are known or follow a guessable pattern. The request is an ordinary API call, up to 500 IDs at a time, and a refused offer leaves no audit entry.

**Smallest source fix.** Name a refused ID only when it is on the cover's own roster, whose people the manager already reads; say any other ID back as it was sent, as the swap check and the pin edit do. After the refusal every remaining ID is in the judged list, so the lookup for the offer rows then holds only this roster's nurses. Add a regression test that offers a cover to the hospital ID of a nurse placed in another unit and asserts that the 422 holds the ID and not that nurse's name. The code below replaces lines 94-100 of offer(); it was written from source and has not been run.

### 3. The downloadable backup carries every live session, so its holder can act as any signed-in user

- **Severity:** low (likelihood low, impact medium); confidence high
- **Fingerprint:** `backend/ops/backups.py:dump_database:live-session-rows-in-downloadable-backup`
- **Source location:** entry `backend/ops/api.py:150`, sink `backend/ops/api.py:121`
- **Lower-trust principal:** A System Admin signed in to the application, or a person holding a recent off-server copy of a backup.

The nightly backup is a pg_dump of the whole database with no table left out, so it includes the django_session table: one row for every browser signed in at that moment, keyed by the value of that browser's session cookie. The System Admin downloads any backup from the health page, and sets the time of day the next one is taken. A System Admin, or anyone else who comes to hold a copy while a session in it is still alive (twelve hours from that session's last request), can read a session key out of the dump, send it as the session cookie and be the CNO, the Deputy CNO, a unit manager or a nurse until that session ends.

What this adds to the role's documented reach is narrow and is all that is claimed. The design already lets the System Admin download the whole database, and already lets them reset the password of a CNO, Deputy CNO or unit manager and sign in as them. That reset is logged under the System Admin's own name, forces a password change and locks the real user out, so it is seen. Taking a session from a backup leaves only `backup.downloaded` (and `technical_settings.changed` if the time was moved), both routine entries; every audited act done with it is entered under the victim's name, told apart only by the client address the audit log keeps beside each entry (backend/audit/log.py:25-26), which is the replayer's and which only the System Admin's audit page shows (backend/audit/api.py:15); the victim keeps working and is shown nothing; and it reaches staff nurses, whose accounts the System Admin does not otherwise manage. The install guide tells whoever keeps off-server copies that a backup holds password hashes and leave, not that a fresh one is a set of working logins.

**Root cause.** `ops.backups.dump_database` runs pg_dump with no `--exclude-table-data`, so session rows, which are live bearer credentials and useless to a restore, are written into a file that is handed over HTTP to a role and copied off the server.

**Intended behaviour.** A backup should hold what a restore needs and no credential that works as it stands. The System Admin manages accounts and operations and 'sees no roster' (docs/ARCHITECTURE.md:127, GLOSSARY.md:63); taking over a managed account is meant to go through the audited password reset, and nurses' accounts are not theirs to manage (backend/accounts/api.py:29-30).

**Conditions.**
- _authorization_role_: The actor is the System Admin (or has their session), or holds a copy of a backup taken off the server.
- _timing_dependency_: The victim was signed in when the backup was taken and their session has not since ended: twelve hours without a request, a logout, a password change or a deactivation ends it; the key must still be a live row on the running server when it is replayed.

**Bounded local reproduction (sandbox, dummy data).**
1. In the DB sandbox (config.test_settings, throwaway Postgres 18), harness-session-in-backup.py signed a dummy staff nurse in with django.test.Client, keeping session_key szf31322huqq5ehh06aixaouobpeb4qf.
2. It then called the project's own ops.backups.dump_database into /scratch: a 376657-byte custom-format dump, the same call the nightly worker job runs.
3. pg_restore --data-only -t django_session on that dump returned exit 0 and the dummy nurse's session_key appeared verbatim in the restored rows: the live key is recoverable from the backup.
4. A fresh django.test.Client with enforce_csrf_checks=True, carrying only that recovered key as the `sessionid` cookie, received 200 from GET /api/auth/session identifying the user as 'dummynurse'. That route is open to anyone (auth=None, backend/accounts/api.py:96) and answers with `request.user`; a role-guarded route and an unsafe method were not run. authz.py reads the same `request.user` and binds the request to nothing but the session key, so by source the same holds for any role (CNO included).

**Observed result.** Demonstrated end to end in the sandbox, not inferred: ops.backups.dump_database (pg_dump, no --exclude-table-data) wrote the django_session rows into the dump; `pg_restore --data-only -t django_session` recovered a signed-in user's live session_key from that dump; and that key, presented as the `sessionid` cookie to a fresh CSRF-enforcing test client, authenticated the request as that user (GET /api/auth/session -> 200, username 'dummynurse'). No deployment was contacted and no real session was used; the dummy principal, dump and replay were all created in the throwaway database.

**Impact.** Full use of another user's signed-in session, the CNO's included, with every audited action entered under that user's name and nothing shown to them; only the client address on the entry, which the System Admin alone reads, is the replayer's. The same actor can already reach the data in the dump and can already take a managed account by an audited reset, so the gain is acting under another's name with next to no trace, and as nurses, not new data.

**Priority rationale.** Needs a System Admin acting in bad faith or their account taken over, or a fresh off-server copy in the wrong hands, and a victim signed in within the last twelve hours. No outside or lower role reaches a backup.

**Smallest source fix.** Leave the session rows out of the dump: add `--exclude-table-data=django_session` to the pg_dump argv, so the table is restored empty and a restore signs everyone out, which is what a restore should do anyway. Add a test that the argv carries it, and say in deploy/INSTALL.md what a backup still holds (password hashes, the push key, every nurse's data).

### 4. A staff nurse who proposes and withdraws the same swap 25 times pushes a named colleague's earlier notices out of the only list that shows them (the unit manager's branch was observed for one round)

- **Severity:** low (likelihood low, impact low); confidence high
- **Fingerprint:** `backend/swaps/steps.py:propose:no-bound-on-propose-withdraw-rounds-notifying-chosen-recipients`
- **Source location:** entry `backend/swaps/mine_api.py:211`, sink `backend/notifications/api.py:70`
- **Lower-trust principal:** A signed-in Staff Nurse using only her own session and the two swap routes the Swaps page uses.

Who: a signed-in Staff Nurse on a unit whose roster for this month or a later one is approved and still has a date of today or later. She needs one change the roster accepts: cells of hers and a colleague's on the same roster, or a cell of her own alone.

What she does: POST /api/swaps/mine with that change, then POST /api/swaps/mine/{swap_id}/withdraw, and the same body again. The only rule about other swaps is that a cell cannot be in two swaps that still wait, and a withdrawal frees it at once. Nothing counts a nurse's swaps or spaces them out.

What was observed in the database sandbox with dummy accounts (Badr proposing, Emad named, unit ER, June 2026): 25 rounds on the very same two cells all answered 201 then 200. The same cells proposed while the first swap still waited answered 422, which is the one bound in the path. Emad received `proposed` then `withdrawn` each round, 50 notices in all. Before the rounds Emad held one unread notice written by the application's own sender ("Mona Ali approved the ER roster for June 2026."). After round 24, GET /api/notifications listed 49 items including it. After round 25 it listed 50 items, all of them Badr's swap notices, and the earlier notice was no longer listed although it was still unread. `unread` and GET /api/notifications/unread both said 51, so the bell counts a notice the page cannot show. The row still exists: POST /api/notifications/{its id}/read answered 204, but a reader has no way to learn that id once it has left the list.

The manager's branch was observed for one round only: a swap of Badr's own cell alone went straight to `awaiting_manager`, and the manager was told `awaiting` then `withdrawn`. With 48 fixture rows placed in the manager's list beforehand (written by the harness, not by any request), that one round took her list from 49 to 50 items and her earlier application-written notice dropped out. That 25 such rounds do the same from an empty list follows from the same two notices a round and the same list query; it was not run.

What is lost and what is not: the notice, not the fact. Each notice points to a page that still shows what it was about (My roster, Swaps, Covers, My month, the unit's pages), and nothing is deleted from the table for a year. A reader who relies on the Notifications page to learn that something happened (a cover offered, a request decided, a roster sent back) will not see it there. No other route lists older notices, pages the list, groups by sender or lets a reader remove a row.

Every round is attributable: two audit entries with the proposer as actor (50 `swap.*` entries by Badr after 25 rounds) and her name in each of the 50 notices. Each round also leaves a withdrawn swap that the colleague's Swaps list returns (25 rows after 25 rounds).

Not observed here and not part of this verdict: whether a phone alerts again at each round (no push service or worker ran; from source a push is sent only while the swap still waits, and the same kind replaces itself on the device), any slowdown or storage growth, and how many colleagues one body can name on a real roster (the cap is 62 cells; one colleague was used). From source, a recipient who is a staff nurse has no way to stop the sender, and nothing limits the swaps themselves. A staff nurse's account is ended only through her end date, a CNO-only route (backend/nurses/api.py:273), and the System Admin's deactivation covers the CNO, Deputy CNO and Unit Manager roles only (backend/accounts/api.py:200). The unit's manager and the CNO do hold an interruption, not exercised here: resetting the password of a staff nurse of the unit (backend/nurses/api.py:383) ends her sessions and leaves the new password with whoever reset it, so she cannot sign in until it is handed to her. That stops further rounds only for as long as the password is withheld; it limits nothing once she is back in, and it brings no displaced notice back into the list.

A request limit in front of the application, which the repository does not have and an installation might add, would not decide this: the effect depends only on the count of accepted requests (50 for an empty list, fewer for a fuller one), nothing in the path needs them to be quick, and a waiting swap stays withdrawable until its earliest date passes, so the rounds can be spread over hours or days at the pace of ordinary use.

**Root cause.** `swaps.steps.propose` and `swaps.steps.withdraw` bound a swap only per cell and only while it waits (`swaps.judging.SwapMonth.in_other_swaps` reads cells of swaps in a WAITING state alone), never per proposer over time. Each accepted step writes one new row into each recipient's notifications through `notifications.sending.swap_step` and `notify`, with no look at what the same sender or the same cells already caused. The reader's side assumes few notices: `notifications.api.list_notifications` returns one fixed window of the newest 50 with no paging, no preference for unread rows and no collapse by swap or sender, while the unread count is taken over every row.

**Intended behaviour.** One user should not be able to decide what another user's notification list shows. Either repeated propose-and-withdraw rounds by one nurse are limited or collapsed so they cannot fill a recipient's list, or a reader can still reach every notice she has not read, however many newer ones arrive.

**Conditions.**
- _authentication_level_: A signed-in session of the application; CSRF token sent as the SPA sends it.
- _authorization_role_: Staff Nurse, placed on a unit for the month of the swap.
- _data_state_: The unit's roster for this month or a later one is approved and has a date of today or later, and one change exists that the roster's rules accept: a cell of hers together with a cell of a staff-nurse colleague on the same roster (to reach that colleague), or a cell of her own alone (to reach the unit's manager).
- _data_state_: The effect on a recipient is the loss from view of notices older than the 50 newest; a recipient with fewer than 50 notices loses one earlier notice for each notice beyond the 50th.

**Bounded local reproduction (sandbox, dummy data).**
1. In the database sandbox only (throwaway PostgreSQL 18, no egress, `config.test_settings`): run `tools/sandbox-db-run.sh v16-p3 harness-swap-rounds-v.py`. It builds the solver's four-nurse sample as unit ER with a dummy manager, June 2026 approved as the project's sound roster, and moves the hospital's clock in the process to 2026-05-15 as the project's tests do, because the fixture month is June 2026. The push service is a stub that raises and no worker runs.
2. The application's own sender writes one earlier notice for the colleague and the manager (`notifications.sending.roster_approved`).
3. Signed in as the dummy nurse Badr with CSRF enforced, send the first payload, then the second with the returned id; repeat 25 times, stopping at the first answer that is not 201 then 200. In round 1 also send the first payload once more while the swap waits.
4. Signed in as the dummy colleague Emad, GET /api/notifications after round 24 and after round 25, GET /api/notifications/unread, then POST /api/notifications/{earlier notice id}/read.
5. For the manager's branch, once: place 48 fixture rows in the manager's list, send the third payload as Badr and withdraw it, and GET /api/notifications as the manager before and after.

**Observed result.** Run once; output in check-swap-rounds-v.txt. All 25 rounds on the same cells answered 201 then 200; the same cells while the first swap waited answered 422. Emad was told `proposed`, `withdrawn` alternately, 50 times; Badr and the manager were told nothing by these rounds. After round 24 Emad's list: items=49, unread=49, the earlier roster-approved notice listed and unread. After round 25: items=50, all `swap_step` with two distinct texts naming Badr, the earlier notice not listed, unread=51 (the unread route agreed), and the earlier row still in the table unread. Marking it read by id answered 204; the list still did not show it and unread fell to 50. Emad's GET /api/swaps/mine returned 25 rows, all withdrawn. Rows: 25 swaps, 50 cells, 25 participants, 50 `swap.*` audit entries, all with Badr as actor. Manager's branch: the own-cell proposal answered 201 with state `awaiting_manager`, its withdrawal 200, the manager was told `awaiting` then `withdrawn`, and her list went from 49 items with her earlier notice listed to 50 items without it, unread=51. The whole run took 6.5 seconds. No bound appeared before the claimed count. Pushes, a second device alert and any load effect were not exercised.

**Impact.** One recipient at a time loses sight of her earlier notices on the Notifications page, with no way to bring them back. A staff-nurse recipient cannot stop the sender herself. From source, not exercised: a Unit Manager, for a staff nurse who belongs this month to the unit she holds, or the CNO can interrupt the sender by resetting her password (backend/nurses/api.py:383-404), which ends her sessions and keeps her out until the new password is handed to her; and the CNO alone can end her account by setting her end date to today or earlier (backend/nurses/api.py:273-302), which ends her sessions and stops her rounds for as long as that date stands. Neither is a limit on the swaps of a nurse who is signed in, and neither restores a displaced notice. No data is disclosed, changed or deleted: the rows stay in the table, the pages the notices pointed to still show the facts, and the bell still counts them. The reach to many colleagues in one body, repeated phone alerts and any load effect were not demonstrated.

**Priority rationale.** The work is trivial (50 ordinary requests, no timing, no special tool) and the precondition is the normal state of a unit with an approved roster. But it takes a signed-in member of the same unit acting on purpose against a colleague or her own manager, every notice names her, and every round is in the audit log under her account. A comparable conventional web application with per-user notices shares the pattern of an unpaged newest-N list often enough that this is a design weakness rather than a broken control; that calibrates the score and is not a reason to dismiss it.

**Smallest source fix.** Fix both sides, since either alone leaves a gap. Sender's side: stop one proposer's rounds from writing an unbounded run of notices. The smallest change is to keep one notice per recipient per swap (at a withdrawal, update or remove the recipient's still-unread `proposed` or `awaiting` notice for that swap instead of adding a second row), together with a small cap on how many swaps one nurse may withdraw on one roster within a day, refused with a plain 409. The cap's number is a product decision. Reader's side: make every unread notice reachable whatever arrives after it, for example by letting GET /api/notifications take an older-than marker so the page can load more, or by listing unread rows first; and collapse consecutive notices about the same swap into one line. Add a test that runs two rounds on the same cells and one that fills a list past 50 and still finds the oldest unread notice.

### 5. A unit manager whose nurse profile has ended keeps reading that unit's rosters after losing the unit

- **Severity:** low (likelihood low, impact low); confidence medium
- **Fingerprint:** `rosters.reading_api.in_force:ended-nurse-profile-keeps-unit-roster-read`
- **Source location:** entry `backend/rosters/reading_api.py:318`, sink `backend/rosters/reading_api.py:334`
- **Lower-trust principal:** A signed-in Unit Manager account that holds no unit and whose own nurse profile ended before the month asked for, in the unit it used to manage.

My roster (GET /api/rosters/mine) and its print sheet show a signed-in nurse the whole approved roster of the unit their month falls under: every nurse's hospital ID, name and shift on each day. Which unit that is comes from the nurse profile's placements alone; the profile's end date, defined as the last day a nurse is part of her unit, is not read. For a Staff Nurse this does not matter, because a passed end date deactivates the account. For a Unit Manager with a nurse profile it does: the end date leaves the account active by design, and nothing else stops the read. A local run in the database sandbox reproduced it with dummy accounts: a manager with a nurse profile in unit ER, the profile ended on a past day by the CNO, the unit then given to another manager by the CNO, and the unit's roster of the next month solved, submitted and approved. The former manager's manager pages refused her (empty unit list, 403 on the unit's roster), but GET /api/rosters/mine for that month answered 200 with the unit's name and all four nurses' hospital IDs, names and shifts, and the sheet endpoint answered the same way. The same end date on a staff nurse of the unit deactivated her account and her read then got 401. Every step that builds the state is an ordinary CNO, manager or approver action that the endpoints accept without a refusal. The gap is low severity: only a CNO can create the state, the System Admin can close it by deactivating the account, and it shows names and shifts only, to someone who used to manage the unit. A manager who holds no unit but whose profile has not ended reading the same pages is intended (backend/nurses/leave_api.py:399-400; docs/ARCHITECTURE.md:712), so the defect is only that the end date is ignored. One later month was run; that the read continues for every later approved month, and that taking the manager off with no successor or a deactivation followed by a reactivation lead to the same state, comes from reading source, not from the run.

**Root cause.** rosters.reading_api.in_force resolves the reader's unit with membership.placement_in(nurse, month), which returns the latest placement begun by that month and never reads NurseProfile.end_date. The only thing an end date does to access is deactivate the account, and nurses.api.set_end_date and nurses.tasks.close_ended_nurses do that for the staff_nurse role alone, while the nurse-reader endpoints also admit unit_manager.

**Intended behaviour.** The end date is the last day a nurse is part of her unit (GLOSSARY.md:27), a unit manager sees nothing of other units and a manager account with no unit assigned can log in but do nothing (docs/ARCHITECTURE.md:123-127). A profile whose end date is before a month begins should give its holder no roster of that month, as a staff nurse's deactivation already does. No document or test says an ended manager profile should keep the read.

**Conditions.**
- _authorization_role_: The reader is an active Unit Manager account that has a nurse profile.
- _data_state_: The CNO has set an end date on that profile that has passed, and the manager no longer holds the unit (in the run, the CNO gave it to another manager). The profile has not been transferred to another unit, and the System Admin has not deactivated the account.
- _data_state_: The unit has an approved roster for the month asked for, which is this month or a later one.

**Bounded local reproduction (sandbox, dummy data).**
1. Run harness-ended-manager.py in the database sandbox (throwaway PostgreSQL 18, no network, config.test_settings). It builds the scene the way the project's tests do (solves/tests/conftest.py, rosters/tests/test_review.py): the four-nurse sample unit, the scripted solver in place of the solver service, and the hospital's today moved to 2026-05-15.
2. As the CNO: POST /api/units creates ER with manager mona (201); POST /api/nurses/managers gives mona a nurse profile in ER (201); PUT /api/nurses/<mona>/end-date sets 2026-05-10, a day already past (200, is_active stays true); PUT /api/units/<ER> gives the unit to manager omar (200).
3. As mona, controls: GET /api/units answers an empty list and GET /api/units/<ER>/roster?month=2026-06 answers 403 "This is not your unit."; GET /api/rosters/mine?month=2026-06 already names the unit ER, with no roster yet.
4. As omar: POST /api/units/<ER>/solves for 2026-06 (201), the solve run with the scripted result, POST roster/submit (200). As the CNO: POST roster/approve (200).
5. As mona: GET /api/rosters/mine?month=2026-06 and GET /api/rosters/mine/sheet?month=2026-06, and read the status and body.
6. Contrast: the CNO sets the same end date on staff nurse Emad of the same unit, and Emad repeats her GET /api/rosters/mine with the session that answered 200 a moment before.

**Observed result.** Observed locally in one sandbox run (check-ended-manager.txt). With mona an active unit_manager holding no unit, her profile ended 2026-05-10 and still placed in ER, GET /api/rosters/mine?month=2026-06 answered 200 with unit "ER", version 1, `mine` null and four rows giving the hospital ID, full name and daily shift codes of Amal, Badr, Dana and Emad. GET /api/rosters/mine/sheet?month=2026-06 answered 200 with a sheet. Her manager pages refused her in the same state (empty GET /api/units, 403 on the unit's roster). The same end date on staff nurse Emad set is_active false and her GET /api/rosters/mine went from 200 to 401. Only that one month was requested; no later month, and neither the no-successor nor the deactivate-then-reactivate route, was run.

**Impact.** Read-only disclosure of one unit's hospital IDs, names and shifts for later months, to a former manager and member of that unit who still has an active hospital account. No leave type, attribute or write is reachable; a colleague's leave reads as a day off.

**Priority rationale.** The reader cannot create the state. It needs the CNO to end a manager's nurse profile and take the unit from her while the System Admin leaves the account active and the profile is left where it is. Each of those is an ordinary action the app accepts, but the combination is uncommon.

**Smallest source fix.** Make the nurse reader's unit depend on the profile's dates as well as its placement: in rosters.reading_api.in_force, give no unit for a month that begins after the profile's end date, keeping the month the end date falls in and earlier months readable as they are now. My roster, its sheet and My month all go through in_force, so one change covers them. in_force has two more callers, both open to staff nurses only: the swap composer (backend/swaps/mine_api.py:148) and what the roster kept of a nurse's preferences (backend/requesting/preferences_api.py:73). Both already answer for a month with no unit or no version in force (the composer says the reader is on no unit's roster, the other returns none), so they need no change, but the new condition applies there too, and to a staff nurse whose end date is still to come: while the account is active, a month that begins after that end date will no longer be read or offered for a swap. Update the `unit` field descriptions of MyRosterMonth, MyRosterSheet and MyMonth to say it is also null after an end date. Add a regression test in backend/rosters/tests that a manager with an ended profile and no unit gets `unit: null, roster: null` for a later approved month, and that a manager with a running profile and no unit still reads theirs. The change below was not run.

## 5. Hardening notes and positive patterns

### Hardening notes (not findings)

These came out of the hunters' source review. None has a demonstrated boundary violation; they are ordered by how much they would reduce the leads above.

**Edge and transport**
- Send `Strict-Transport-Security` when `DOMAIN` is set, and a `Content-Security-Policy` with `frame-ancestors 'none'` (or Django's `XFrameOptionsMiddleware`) on every response. `backend/config/settings.py`, `deploy/Caddyfile`.
- State limits in `deploy/Caddyfile` instead of leaving defaults: a request-body size cap, request buffering sized for the largest import, a body read timeout, and a per-client rate limit on `POST /api/auth/login`. Consider threaded gunicorn workers so one slow request cannot hold a third of the pool. `deploy/compose.yaml:52-55`.
- With `DOMAIN` empty, `ALLOWED_HOSTS` is `["*"]` and Caddy issues an internal certificate for any name a client sends. Accept an explicit list of the server's own names for LAN-only installs. `backend/config/settings.py:22-30`, `deploy/Caddyfile:10-14`.
- `GET /api/health` is anonymous and calls the solver on every request with a 2 s timeout; cache the answer for a few seconds or split liveness from the solver check. `backend/ops/api.py:45-50`.
- The second gate on `/metrics` assumes the only proxy always adds `X-Forwarded-For`; a scrape token or a Host check would not depend on that. `backend/ops/metrics.py:57-63`.

**Accounts and sessions**
- Anyone can keep a named account locked by sending five wrong passwords every fifteen minutes (the lock is keyed by username alone). A per-client limit before the lock would remove that lever. `backend/accounts/login.py:34-36`.
- A failed login stores the submitted username in the audit log, so a password typed into the username box is kept and readable by the System Admin. Record the typed value only when it names an existing account. `backend/accounts/login.py:55-57`.
- Sessions have a 12-hour idle limit but no absolute lifetime. A password reset or change does end the account's other sessions (through Django's session hash; asserted in `backend/accounts/tests/test_users.py`), but it leaves the account's push subscriptions in place. `backend/config/settings.py:97-98`, `backend/accounts/provisioning.py:174-184`.
- `POST /api/auth/change-password` checks the current password with no failure counter; `INITIAL_ADMIN_PASSWORD` is accepted without the password policy and stays in the web container's configured environment; generated passwords never expire before first use. `backend/accounts/api.py:125-143`, `backend/accounts/management/commands/bootstrap.py:27-32`, `deploy/compose.yaml:54-58`.
- A staff nurse's access ends on the end date only through the hourly `close_ended_nurses` job; a request-time check of the end date would not depend on the worker being up. `backend/nurses/tasks.py`, `backend/units/scope.py`.

**Data and operations**
- After a restore, accounts deactivated since the backup are active again and replaced passwords work again (reproduced in the sandbox; rejected as a finding because the restoring operator is trusted and this is inherent to restoring a database). Have `deploy/restore.sh` empty `django_session` and the login-attempt table, print the deactivations, resets and key rotations recorded after the backup's moment before the replaced database is dropped, and say so in `deploy/INSTALL.md`.
- The application connects as the role the Postgres image creates, which is a database superuser, and the audit log is append-only by convention only. A separate non-superuser role with `UPDATE`/`DELETE` revoked on the audit table would enforce it. `deploy/compose.yaml:131-133`.
- The VAPID private key is stored in the database and therefore in every backup; `deploy/INSTALL.md` should list what a backup holds (password hashes, the push key, every nurse's data).
- Compose sets no `cap_drop`, `no-new-privileges` or `read_only` on any service; images and GitHub Actions are pinned by tag, not digest/SHA; `browser-checks.yml` runs `npx --yes playwright@…` outside the lockfile. `deploy/compose.yaml`, `Dockerfile`, `.github/workflows/`.
- `.gitignore` covers `.env` only and `.dockerignore` has no `**/.env*` rule; `backend/config/test_settings.py` (default secrets, MD5 hasher) is copied into the production image, inert unless selected. `.gitignore`, `.dockerignore`, `Dockerfile:22`.
- Several handlers take the hospital-wide `HospitalSettings` row lock and body-named nurse row locks before their scope check (`backend/rosters/api.py`, `backend/requesting/deciding.py`, `backend/nurses/leave_api.py`, `backend/swaps/steps.py`). Measured at 50–125 ms per refused swap proposal; refuse from a plain read first, and set a `lock_timeout` for web connections.
- No CNO or System Admin route can cancel another unit's queued or running solve; `Solve.error` returns `str(e)` of unexpected worker exceptions to the manager; a solver result becomes a draft on the solver's own `ok` flag without re-validation in the worker. `backend/solves/api.py`, `backend/solves/running.py`.
- Cap push subscriptions per user and give one push job a send budget; align the `auth` key length between `push_api.py:27` (200) and the model column (100); make `pushing.send` catch any library exception as its docstring promises.

**Functional defect found on the way (not a security finding)**
- A roster left submitted past its month can still be approved by the CNO or Deputy CNO; if the following month has already closed, that unit's month close is then refused for good (reproduced in the sandbox with dummy data; rejected as a security finding because the actor is trusted with approval). Refuse approval of a roster whose month is over, or let the close chain tolerate it. `backend/rosters/review.py`, `backend/closes/making.py`.

### Positive source patterns

- Every API route is authenticated by default (`NinjaAPI(auth=SignedIn())`), and `backend/accounts/tests/test_authorization.py` walks every endpoint for the public allow-list, role refusals, signed-out 401 and missing-CSRF 403.
- Unit scope is one function (`units_in_scope` / `unit_in_scope`) called per handler, with secondary ids filtered by unit; cross-unit refusals look the same as "does not exist". All 27 route files were reviewed; the final critic independently read six scoped routes across five apps and found each matched the ledger's check on where scope is enforced.
- No raw SQL with user input, no `eval`/pickle/yaml/`shell=True`, no `dangerouslySetInnerHTML` or `innerHTML`, nothing sensitive in `localStorage`; `pg_dump` is run with an argv list.
- CSV and XLSX exports neutralise formula cells and quote everything; download filenames go through `content_disposition_header`; password sheets are `no-store`.
- Push addresses are checked against a host allow-list at subscribe time and again at send time with redirects off (a parser-differential candidate was tested offline and rejected); pushes carry a kind code only.
- The solver requires a bearer token on every path with constant-time comparison and refuses to start without one; only Caddy publishes ports and the app networks are internal; the application containers (web, worker, solver) run as uid 1000.
- CI runs with `contents: read`, no secrets, no `pull_request_target`, and builds the image with `push: false`.
- Backup download names are regex-checked and symlinks refused; backup files are mode 0600 in a 0700 directory.
