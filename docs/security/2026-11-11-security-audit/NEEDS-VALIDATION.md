# Needs validation — cp-sat-nurse-roster-app

Prioritised leads without severity. Each is grounded in source and was checked by two independent agents; each waits on a fact this run could not observe. None is a confirmed vulnerability. The deployment checks are for the owner to observe on their own installation; they are not instructions to probe a live system.

## 1. Refused anonymous logins leave committed rows that nothing removes, and a locked name takes them without a password hash

`backend/accounts/login.py:attempt_login:audit-and-attempt-rows-never-pruned`

**Affected boundary.** Anonymous client → database storage

Checked in the database sandbox with 18 login requests and dummy names. An anonymous client that first calls GET /api/auth/session for the CSRF cookie gets 401 for an unknown username, and that one request commits one audit row (auth.login_failed, no actor, the tried name as target) and one LoginAttempts row keyed by the name; both were still there after the connection was closed and reopened. Without the CSRF cookie and header the answer is 403 and nothing is written; a 151-character name is 422 and nothing is written; a 150-character name of four-byte characters and a name outside the account pattern are both stored as sent. After five failures the name is locked for 15 minutes, and every further request to it, from any client and with any password, is 423 and adds one audit row with reason locked while calling neither authenticate nor the password hasher (0 calls counted, against 1 for each unlocked refusal). This held for a real account and for a name that is no account. The LoginAttempts row is not changed by locked requests. Measured sizes on disk: a locked refusal's audit row is 104 to 120 bytes with a 9 to 12 byte name and a wrong-credentials one 136 to 152 bytes, plus four index entries (key, at, actor, action with id; the hunter counted three) of 88 to 96 bytes together and 20 bytes of line pointers, so about 0.2 to 0.3 KB per refused request; with a 600-byte name the audit row was 736 bytes, about 0.85 KB with its index entries. A LoginAttempts row is 34 to 48 bytes for a short name and 630 bytes for the 600-byte name, once per name, with two index entries on the key; those two measured only 32 bytes each for the long name because the test name was one character repeated, which the index compresses, and a varied name was not measured. There is no amplification per request: a kept row is about the size of the request that made it. For audit rows on names already tried, that is roughly 1.2 to 5 million refused requests per gigabyte of database; a new long name on every request also stores the 630-byte LoginAttempts row and its two key entries, which brings it under a million, at the price of one password hash each. The bytes each row adds to a nightly dump were not measured. Source shows no removal: the only LoginAttempts deletes are a successful login and a password reset of that name, no code deletes an AuditEntry, and none of the scheduled jobs deletes from either table; no throttle is in the middleware, the API or the Caddyfile. What this adds to the password-hash record for the same route is what stays after the requests stop: rows that stay for good, copied into every kept whole-database dump on the one disk the database, the backups and everything else share, with no way in the application to remove them (an operator can delete them by hand in psql; nothing in the database prevents it). The principal that would be affected is every user of the installation, if that disk fills and the database can no longer write; the System Admin is affected less, by a log whose newest pages are refused logins and by two reads that scan the table (the filter by user and the list of actions), which get slower and do not fail. As calibration and not as grounds to dismiss: the comparable baseline accepts a username-keyed lockout, and apps of that kind commonly keep a row per failed login, but the architecture summary does not say it accepts rows that never expire with no limit on attempts per client. Auditing every failed login, locked ones included, is the stated design and a test pins it, so the open question is not intent. It is whether a deployment accepts millions of such requests from outside before anyone sees the disk and database gauges move. That depends on the request rate the installation serves, the size of the disk, the backups kept and any limit in front of Caddy, none of which may be measured by volume here. Without that fact this is a hardening item (cap or sample the audit rows written while a name is locked, expire LoginAttempts rows for names that are no account, limit attempts per client); with it, an anonymous, lasting loss of availability.

**Claimed root cause.** backend/accounts/login.py records every refusal, including each refusal while a name is locked, into an audit table that is never pruned, and keeps one LoginAttempts row per distinct attempted name with no expiry; nothing in the repository limits how many such requests one client may make.

### Source trace

1. **entrypoint** `backend/accounts/api.py:103` (`login`) — POST /api/auth/login is auth=None; LoginBody (lines 68-78) accepts any username of 1 to 150 characters without NUL and passes it to attempt_login. Observed: 401 for an unknown name, 422 at 151 characters, 403 without the CSRF cookie and header.
2. **propagation** `backend/accounts/login.py:32` (`attempt_login`) — get_or_create inserts a LoginAttempts row for a name not seen before; for a failure it is saved and kept (line 49). Observed: one row per distinct name, committed.
3. **propagation** `backend/accounts/login.py:36` (`attempt_login`) — While locked_until is in the future the refusal is recorded without authenticate being called. Observed: 423, one more audit row with reason locked, zero calls to authenticate and to the password hasher.
4. **sink** `backend/audit/log.py:25` (`record`) — AuditEntry.objects.create appends the row, with the attempted username as target, to a table no code deletes from. The refusal is raised after the transaction block ends (login.py:52), so the row is committed.

## 2. Anonymous login attempts each cost a full password hash on a three-worker pool, with no limit across usernames

`backend/accounts/login.py:attempt_login:preauth-hash-unbounded-across-usernames`

**Affected boundary.** Anonymous client → shared web workers (CPU per login attempt)

POST /api/auth/login is open to anyone. For any username that is not currently locked, known or unknown, the server runs one full password hash inside one of three synchronous gunicorn workers, then stores a login-attempts row and an audit entry. The only throttle is the five-failure lock, and it is keyed by the exact username string the caller submits, so a caller who sends a different username on each request is never throttled. Source shows no other limit: the Caddyfile is a bare reverse proxy, the API and settings configure no throttle, compose sets no CPU or memory limit on any service, and the CSRF check on login reads only values the caller supplies: the token comes from GET /api/auth/session and the headers are the caller's own. The verifier checked the source path and measured the cost once: in the project's runtime image with the production settings module, the hasher is Django 6.1.3's default PBKDF2-SHA256 with 1,500,000 iterations, and one hash took 0.50 s of CPU on this development machine (arm64, sandbox limited to one CPU). The installed Django hashes for an unknown username as well (its timing mitigation), and gunicorn's defaults are the sync worker class with one thread, so each worker serves one request at a time. From these figures, about min(3, number of cores) divided by the hash time, that is roughly two requests a second on a one-core server and six on a server with three or more cores, would keep every worker (or every core) hashing; every signed-in user shares that pool, and on a small server the solver and database share the CPU. Each such request also leaves one login-attempts row per new username and one audit entry, and neither is ever removed for a name that never logs in. Recovery, derived from source and not observed: when the requests stop, the workers are free again once the requests already queued have drained (gunicorn's listen queue defaults to 2048), nothing needs restarting, and what stays behind is the login-attempts and audit rows. What is not established: that other users' requests are in fact delayed (it follows from the source but was not observed, and must not be shown by load); the hash time and core count of the real server; and whether the installation is reachable from an untrusted network or has a rate limit in front of Caddy. A failing container health check would only mark the web container unhealthy; nothing in compose restarts or removes it for that. A stock Django login with the default hasher and no throttle has the same property, which calibrates the severity but does not remove the question. Anyone locking a named account with five wrong passwords is documented and accepted by the owner and is not part of this candidate. If the owner's checks support it, the usual remedy is a limit per client address and in total that applies before the password hash, in Caddy or in the application.

**Claimed root cause.** Login work is budgeted only per submitted username (accounts.login.attempt_login and the LoginAttempts model). Nothing bounds attempts per client or in total before the password hash runs, unknown usernames are hashed too (Django's timing mitigation) and each gets its own counter row that is never removed, so rotating the username escapes the only budget there is.

### Source trace

1. **entrypoint** `backend/accounts/api.py:103` (`login`) — POST /auth/login is registered with auth=None. The body takes any username of 1 to 150 characters without a NUL and any non-empty password (LoginBody, lines 68-78).
2. **propagation** `backend/accounts/api.py:107` (`login`) — The only check before attempt_login is CSRF (django-ninja's check_csrf, which runs Django's CsrfViewMiddleware). Every value it reads comes from the caller: the token cookie is handed out by GET /auth/session (lines 96-100) to anyone, and the X-CSRFToken, Origin and Referer headers are whatever a non-browser client sends.
3. **propagation** `backend/accounts/login.py:32` (`attempt_login`) — A LoginAttempts row is fetched or created, and row-locked, for the exact submitted string, so every new username starts a fresh, unlocked counter and does not wait on any other username's row.
4. **sink** `backend/accounts/login.py:40` (`attempt_login`) — authenticate() runs the full password hash for a known or an unknown username inside the open transaction; on failure lines 46-51 save the counter row and write an audit entry.

### Verified evidence

- `backend/accounts/login.py:34` — The lock test on the per-username row is the only gate between the request and the hash at line 40.
- `backend/accounts/models.py:59` — LoginAttempts is keyed by the username tried, known or not. Its rows are deleted in two places only: a successful login as that name (backend/accounts/login.py:42) and a password reset of that user (backend/accounts/provisioning.py:181). No periodic job removes rows for names that never log in.
- `backend/accounts/login.py:55` — Every refused attempt, locked or not, writes an AuditEntry; backend/audit/models.py:5-8 says entries are never changed or deleted. A refused attempt at a locked name writes its entry without any hash.
- `deploy/compose.yaml:55` — gunicorn runs with --workers 3 and no worker class or threads (backend/config/gunicorn.py sets only logging), so gunicorn's defaults apply: sync workers with one thread, three requests served at a time. The file sets no CPU or memory limit on any service, so web, solver, worker and database share the host's cores.
- `deploy/compose.yaml:49` — The project's own comment sizes the 300-second timeout for password hashes at about half a second each on one core, which matches the measured 0.50 s and shows a one-core server is contemplated.
- `deploy/Caddyfile:21` — The proxy in front is reverse_proxy web:8000 with no rate or connection limit.
- `backend/config/settings.py:87` — Only password validators are configured; PASSWORD_HASHERS and AUTHENTICATION_BACKENDS are not set, so Django 6.1.3's defaults apply. Observed in the runtime image: PBKDF2PasswordHasher, 1,500,000 iterations, ModelBackend.
- `docs/ARCHITECTURE.md:782` — The design document states that one password hash takes about half a second on purpose.
- `deploy/INSTALL.md:35` — The install guide expects installations that are reachable from the internet.
- `backend/accounts/tests/test_login.py:188` — A test pins that an unknown username is counted and locked like a real one. The installed Django's check_password_with_timing_attack_mitigation runs the default hasher when no user is found, so an unknown name costs the same hash.
- `deploy/compose.yaml:64` — The web health check calls GET /api/health through the same three workers, with an 8-second timeout. Nothing in the file acts on an unhealthy state after start-up; restart: unless-stopped applies only when a container exits.

### Exact blockers

- The effect on other users has not been observed: that three hashing logins make other requests wait follows from gunicorn's sync workers in source, but showing it needs the real worker pool with the production hasher. The provided sandbox cannot run that (its database wrapper uses the test settings with the MD5 hasher and Django's test client, not gunicorn), and it must never be shown by load on the shared stack or a real installation.
- Deployment facts are not in the repository: whether the site is reachable from an untrusted network; whether a firewall, WAF, CDN or other rate or connection limit sits in front of Caddy; how many CPU cores the server has; and how long one password hash takes on it. The 0.50 s measured here is this development machine's figure.

### Bounded local plan

Done by the verifier in the no-network, read-only sandbox (one CPU): harness-one-hash.py loaded config.settings with three dummy values and performed exactly one password hash; check-one-hash.txt records Django 6.1.3, PBKDF2PasswordHasher with 1,500,000 iterations, ModelBackend, gunicorn defaults worker_class sync and threads 1, and one hash at cpu 0.502 s, wall 0.502 s. harness-read-mitigation.py read the installed Django as text and confirmed that an unknown username runs the default hasher (check-read-mitigation.txt). Still open, and only for the owner on an isolated scratch stack that nobody else uses, never the shared stack or a real installation: send exactly three concurrent logins with three different unknown usernames and one GET /api/health alongside them, once. The candidate is supported if the health request waits about one hash time, one row per username appears in accounts_loginattempts and in the audit log, and a request sent after the three logins have answered returns in its normal time (recovery). Do not repeat or scale this up.

### Owner-observed deployment check

The owner checks on the real installation, without sending test traffic: whether ports 80 and 443 are reachable from outside the hospital network; whether any rate limit, WAF, CDN or connection limit exists in front of Caddy; how many cores the server has; how long one password hash takes there (one timed make_password call in the web container); and, read-only in the database, whether bursts of auth.login_failed entries with many different targets already appear in the audit log, together with the row count of accounts_loginattempts.

## 3. No frame control on any response: if a same-site origin is attacker-influenced, it could frame the signed-in app and collect the two clicks that approve a roster

`backend/config/settings.py:MIDDLEWARE:no-frame-ancestors-control`

**Affected boundary.** Same-site page → a signed-in user's clicks (framing)

Observed locally (real settings, middleware stack and URL conf at f2492e0, Django 6.1.3, no browser): the SPA document, the files WhiteNoise serves and an API answer carry neither X-Frame-Options nor Content-Security-Policy, with DOMAIN set and with DOMAIN empty, and the SPA document is answered the same when the request declares itself a same-site frame navigation. Django's XFrameOptionsMiddleware is not in MIDDLEWARE, config.urls.spa adds only Cache-Control, deploy/Caddyfile has no header directive, frontend/index.html has no CSP meta, and the front end has no frame check of its own. The comparable baseline (a conventional Django project) sets this header through the middleware.

What this does not give an attacker: a frame on an unrelated site. The cookie settings in force are SameSite 'Lax', Secure and no Domain for both the session and the CSRF cookie, and the CSRF cookie was observed set that way (no session cookie was issued in this run, so its attributes are read from the settings in force). Such a frame is therefore signed out and cannot sign in. A sibling origin also cannot post to the API directly: with a valid CSRF cookie and header, a POST whose Origin is a sibling host was refused 403 'CSRF check Failed' on /api/auth/login and on the approve route itself, in both modes, while the same POSTs with the app's own Origin got past the check (login went on to the absent database, approve answered 401 for no session). Framing is therefore the one route a same-site page would have to this action, which is why the missing header matters at all. One limit on that, by specification and not observed here: cookies are not scoped by port, so a party that runs another https service on the app's own host name or IP at a different port (as opposed to one who can only place content on such a service) is sent the host-only session cookie by the browser on any request to that service. No frame control bears on that case, so for a same-name service the header matters only against content placed on a service someone else runs.

What stays unshown: the boundary effect itself. Nothing was demonstrated beyond the header, cookie and Origin-check facts above. The claim is that a page on a same-site origin (with DOMAIN set: another https host under the same registrable domain, such as another hospital web application; with DOMAIN empty: another https service on the same host name or IP at a different port) could load /unit-roster?unit=<id>&month=<YYYY-MM> in a frame with the victim's session, and lead the victim to click Approve and then the dialog's Approve, which posts /api/units/{unit_id}/roster/approve from the app's own origin. All of these must hold: the victim is a signed-in CNO or Deputy CNO who opens the attacker's page and clicks twice where it leads; the roster of that unit and month is submitted and has no approve refusal (the server re-checks it at approval); the attacker either knows the unit's UUID or relies on the page's fallback to the first live unit; and the attacker can publish or inject content on a same-site origin. Only this one action was traced; other pages' click-only actions were not. If no such same-site origin exists for an installation, this is a hardening gap and not a reachable flaw; the source fix is the same either way (add django.middleware.clickjacking.XFrameOptionsMiddleware, whose default is DENY, or a CSP frame-ancestors 'none').

**Claimed root cause.** backend/config/settings.py MIDDLEWARE omits django.middleware.clickjacking.XFrameOptionsMiddleware, and no other layer (config.urls.spa, WhiteNoise's header hook, deploy/Caddyfile, frontend/index.html) sets X-Frame-Options or Content-Security-Policy frame-ancestors. Framing is limited only by host-only SameSite=Lax cookies, which by specification are still sent to a frame whose embedder is same-site.

### Source trace

1. **entrypoint** `backend/config/urls.py:23` (`urlpatterns`) — Every path outside api/ and metrics is answered by spa, so a deep link such as /unit-roster?unit=...&month=... can be the address of a frame.
2. **propagation** `backend/config/urls.py:14` (`spa`) — The SPA document is returned with Cache-Control as the only header the view adds; observed without X-Frame-Options or Content-Security-Policy.
3. **propagation** `backend/config/settings.py:62` (`MIDDLEWARE`) — SecurityMiddleware, WhiteNoise, sessions, common, CSRF and authentication only; no XFrameOptionsMiddleware and no CSP middleware, so API and static answers carry no frame control either (observed).
4. **propagation** `deploy/Caddyfile:21` (`site block`) — Caddy proxies to web:8000 and the file has no header directive, so the proxy adds none (read from source, not executed).
5. **propagation** `frontend/src/routes/_signed-in/unit-roster.tsx:33` (`Route /_signed-in/unit-roster`) — Unit and month come from the address (and the route is for CNO and Deputy CNO only, line 34), so a framed page would open directly on one unit's month.
6. **propagation** `frontend/src/components/unit-picker.tsx:13` (`useChosenUnit`) — Without a known unit id the page falls back to the first live unit, so the link works without the UUID but then the attacker does not choose the unit.
7. **propagation** `frontend/src/routes/_signed-in/unit-roster.tsx:156` (`RosterView`) — The decision section is rendered only while the roster is submitted.
8. **propagation** `frontend/src/routes/_signed-in/unit-roster.tsx:88` (`Decision`) — The Approve button opens a confirming dialog; it is disabled when the server gave an approve refusal. Both steps are plain clicks with no typed input.
9. **propagation** `frontend/src/routes/_signed-in/unit-roster.tsx:69` (`Decision.confirm`) — Confirming calls approveRoster from the app's own origin, so the request would carry the session cookie, the CSRF token and the app's own Origin.
10. **sink** `backend/rosters/api.py:577` (`approve_roster`) — POST /api/units/{unit_id}/roster/approve needs a CNO or Deputy CNO session, CSRF and a month only; it re-checks the roster and makes it the roster in force. Reached in this run only without a session (403 for a sibling Origin, 401 for the app's own); no approval was made.

### Verified evidence

- `backend/config/settings.py:62` — MIDDLEWARE as configured; the harness printed the same list from the running settings, and every observed answer had X-Frame-Options and Content-Security-Policy absent (Cross-Origin-Opener-Policy: same-origin is present but does not restrict framing).
- `backend/config/settings.py:37` — Only the Secure flags are set; observed in force: SESSION_COOKIE_SAMESITE and CSRF_COOKIE_SAMESITE 'Lax', no cookie Domain, and the CSRF cookie set as SameSite=Lax, Secure, host-only. No session cookie was issued in the run.
- `backend/config/urls.py:16` — The only header spa adds to the SPA document.
- `deploy/Caddyfile:21` — reverse_proxy only; the file contains no header directive.
- `frontend/index.html:3` — The head has no Content-Security-Policy meta element (which could not carry frame-ancestors in any case).
- `backend/accounts/api.py:107` — Login runs check_csrf; observed: a POST with a valid CSRF cookie and header and a sibling Origin is refused 403 'CSRF check Failed', and with the app's own Origin it passes the check (the answer is then a 500 from the absent database, an OperationalError raised inside the view).
- `frontend/src/routes/_signed-in/unit-roster.tsx:101` — The confirming dialog for Approve: a second click, no typed confirmation.
- `backend/rosters/api.py:577` — The approve route and its auth (approver = SignedIn(CNO, Deputy CNO), line 41); the handler refuses with 409 unless the roster is submitted and passes its check (lines 589-591). Observed without a session: valid CSRF pair with a sibling Origin answers 403 'CSRF check Failed', with the app's own Origin 401 'Unauthorized'. So a same-site page cannot post to this route itself and would need the frame.

### Exact blockers

- Deployment fact, outside the repository: whether any same-site origin exists that someone other than the app's operators controls or can inject content into. With DOMAIN set that means another https host under the same registrable domain as DOMAIN; with DOMAIN empty (the default, reached by IP or a bare name) it means another https service on the same host name or IP at another port. The repository names neither the installation's host name nor its neighbours.
- Browser observation not available in this run (no browser in the sandbox): that a same-site, cross-origin frame of /unit-roster carries the host-only SameSite=Lax session cookie, renders the submitted roster signed in, and that the Approve click and the dialog's Approve click inside the frame complete POST /api/units/{unit_id}/roster/approve.

### Bounded local plan

## 4. No limit on one user's push subscriptions, and the one push job sends to each of them in turn under the installation-wide lock

`backend/notifications/subscriptions.py:turn_on:uncapped-push-subscriptions-sent-serially-under-push-lock`

**Affected boundary.** Signed-in user → other users' push delivery

Any signed-in user, of any role, can turn pushes on for as many addresses as they post. POST /api/notifications/push/on keeps a row for each new address on an allowed push-service host and never counts the user's rows; the allow-list takes any name under three domains, so distinct addresses can be made up. Each new row writes one `push.turned_on` audit entry naming the user, the only trace source shows. When a notification of one of the six pushed kinds is later written for that user, the push job sends to every row the user holds, one blocking HTTPS request after another, and the job runs under the lock `push`, which lets one push job run at a time for the whole installation. The readers later in the same job, and every other push job of every unit, wait until it ends.

The time under the lock is the number of rows times the cost of one send, and the requester chooses the number of rows. What the push service answers sets the cost of one send and how long a row lasts: 404 or 410 removes the row at its first send; another 4xx is one send for each notification and the row is removed at the tenth; an address that cannot be reached (no resolution, a refused or timed-out connection, 429, 5xx) is sent to four times for each notification and removed after ten such notifications, so up to 40 sends; a row whose service answers success is never removed by the job.

Checked in this run, in the database sandbox, with dummy users, no network and the push sender replaced by a recording stub as the project's own tests do: a staff nurse stored four made-up addresses under the allowed domains (200 each, `devices` 4, four audit entries; an address off the list was refused with 422, a call with no session and no CSRF token with 403); one request window opened by the manager deferred one job with lock `push` for both nurses of the unit; that job's delivery made the four sends to the first nurse's rows before the one send to the second nurse; with the stub failing to connect, the four were carried on from the first try and from a second, and counted one failure each at the last try (three of the four tries were run, 12 `unreachable` attempts for the one notification; the full course is 16), and all four rows were still held; rows deleted while the job was inside its loop were still sent to. With the stub answering 201 at once one send cost a median of about 3.1 ms, and with it failing to connect at once about 2.4 ms, in the one-CPU sandbox, so in that sandbox a job's time had a floor of about 3 ms a row with no network at all. The figure is the sandbox's, not the installation's.

What it takes: a signed-in account (a staff nurse is enough) to store the rows, and a pushed notification addressed to that account. The account cannot cause one alone, but needs no help: the unit's next request window opening tells every staff nurse of the unit in one job, and a colleague's swap proposal naming one of its cells does too.

What it does not do: the job holds no database transaction and no other kind of job's place (the worker runs four at once and a job waiting on a lock takes none), so solves, the month close and the hourly jobs go on, and every notification is still on the bell. The outcome is late pushes of the kinds that have a deadline (a swap to answer or decide, requests open or to decide, a roster to approve or sent back) for as long as the job runs. The install guide already says a server that cannot reach the push services loses pushes and nothing else.

Not established: what one send to a made-up address costs on the installation's network, and so whether the delay is seconds, minutes or hours for a number of rows a user could store. That is a runtime fact outside the sandbox. The affected principal and the outcome are concrete: every other user with pushes on, in every unit, and their pushes of the six kinds arriving late. Only the duration is open. If it is short for any number of rows an account could store, this is a hardening item (a limit on rows for one user and on the sends of one job); if it reaches many minutes or hours, it is an availability finding against pushes and nothing else. No push was sent and no push service was contacted.

**Claimed root cause.** subscriptions.turn_on stores a row for every new allowed address with no limit for one user, and pushes.deliver has no limit on the sends or the time one job spends on one reader, while the job holds the single lock every push job shares.

## 5. A cross-site page may make a signed-in CNO's browser take the audited staff-list export and learn that the visitor is the CNO

`backend/nurses/files_api.py:GET-attachment-routes:cross-site-download-oracle`

**Affected boundary.** Cross-site page → a signed-in CNO's or System Admin's browser

The file routes are plain GET routes that check only the session and the role. The same request gets a JSON 403 for a staff nurse and a JSON 401 signed out. The session cookie is SameSite=Lax, which is the cookie policy that still sends the cookie on a cross-site top-level GET navigation. If a browser behaves that way here, a page on another site that knows the installation's address and is visited by a signed-in CNO can do two things. It can make that browser fetch the staff list without the user asking: the file (every nurse's hospital ID, name, gender, unit and dates) lands in the device's downloads, and the audit log records an export the CNO did not intend, once per navigation. And it may tell the download from the JSON refusal, which gives it one fact: this visitor is signed in here as CNO. The attacker never receives the file's content. Narrower than the hunter's wording in three ways. First, the CNO's routes are the only ones whose addresses are fixed, so they are the ones any outside page can aim at. The roster export needs a unit's UUIDv7 and an existing version, which an outside page does not have; a signed-in nurse of the unit does know the unit's ID (GET /api/nurses/my-unit), so an insider could aim the same unintended roster.exported row at that unit's manager, though the oracle tells a nurse nothing new. The System Admin's backup download needs the backup's exact name, which carries the second it was taken, but that is less closed than it looks: by source the nightly backup is named from the clock at the moment a job on a five-minute schedule starts, after a backup time that defaults to 02:00 on the hospital's clock, so on an installation with default settings the name is predictable up to the few seconds the job takes to start. That delay was not observed, and a wrong name answers a refusal that replaces the navigating page, so an outside page gets about one guess per visit. A right guess would put a whole backup on the System Admin's own device and write backup.downloaded in their name; the attacker still receives nothing. Second, Cross-Origin-Opener-Policy: same-origin was observed on both the attachment and the refusals, so the popup form of the oracle may be closed by it; it does not cover a page that navigates its own tab and notices it is still loaded. Third, the role of a hospital's CNO is not a secret in itself, so the oracle is worth little alone; the unintended audited export is the firmer effect. If the browser check confirms it, this is a low-severity finding, and a same-origin test on Sec-Fetch-Site for every file route, the backup download included, would close it without touching the app's own links, which are same-origin.

A solve another unit's manager started afterwards for 2027-01 reported queue_ahead 3, and the queue's own fetch function handed out the three earlier jobs first, one at a time, and that unit's job last; while one solve job was marked as running, a second fetch returned nothing. The other manager's stop request was refused (403 through the first unit's URL, 404 through their own), and the CNO, the Deputy CNO and the System Admin were each refused with 403; the solves stayed queued. The API has one route that ends a solve, stopSolve, and it is the owning unit's manager's. While the solves waited, the CNO's change of the hours of a shift that unit works was refused with 422, naming the four waiting months. What was refused before queuing: the same unit and month again (409), a past month (409), a year after 2076 (422), a time limit above the cap (422), and a unit with no nurses in the month (409). A far-future month is therefore not refused for having no data: a unit whose nurses have no end date has nurses in every month. What was not observed, and decides the size of the effect: how long each such solve holds the lock once it runs. By source it is at most the stored time limit plus 120 s per attempt, and the search ends earlier only when CP-SAT proves the roster optimal or infeasible. The solver's own notes say the four-nurse sample is proven optimal in well under a second, while the 25-nurse ER rule set still had an unproven gap after 30 s. So the delay imposed on other units lies between a few seconds and the full limit for each queued solve: about 600 x 300 s, roughly 50 hours, at the default cap is an upper estimate, not a measured result. The manager also writes their own unit's rules, which influence how hard the search is. Each start is written to the audit log with the manager's name, and the first-come-first-served order across units is documented design (ADR 0009, architecture section 7) and tested; what is not bounded is how much of the queue one unit can hold. Recovery by anyone but the owning manager is indirect: the CNO can assign the unit another manager, who can then stop each solve one by one, or an operator works in the database.

**Claimed root cause.** Solve admission bounds concurrency per (unit, month) only, over a month range of about fifty years, while execution is serialised hospital-wide in job-id order with no per-unit or per-requester share, no limit on how far ahead a month may be solved, and no cancel route for a role above the unit.

## 7. A sign-in request whose body has not arrived occupies one of the three web workers; whether this is reachable through Caddy is not settled

`deploy/compose.yaml:web-gunicorn-sync-workers:unbuffered-request-body-holds-worker`

**Affected boundary.** Anonymous client → shared web workers (held connection)

The application is served by three gunicorn workers of the default synchronous class with a 300 second worker timeout, behind a Caddy reverse_proxy that sets no request buffering, body limit or read deadline. POST /api/auth/login needs no sign-in and declares a JSON body, which the API layer reads before the handler's own checks run. Verified locally (no-network sandbox, no Caddy, no database): with the compose command line reduced to one worker on loopback (gunicorn 26.2.0, Django 6.1.3, django-ninja 1.7.3, 'Using worker: sync', --timeout 300), one anonymous login that declared 64 body bytes and had not sent them received no answer for 2 seconds, and a second request (GET /api/auth/session) sent meanwhile stayed unanswered for 6 seconds. When the 64 bytes were then sent, the login was answered at once (403, no CSRF cookie) and the waiting request was answered (200). No worker timeout was logged. So the worker waits on the body and serves nobody else while it does. Not observed, and stated as inference only: that the wait lasts up to 300 seconds (from the --timeout flag and the installed sync worker, which reads from a blocking socket with no deadline and is only ended by the arbiter's timeout), and that three such requests would leave no worker for other users or for the web health check. Not established at all: whether Caddy 2.11 with this Caddyfile passes a request to web:8000 before its body is complete. web:8000 is not published, so if Caddy completes bodies first, or something in front of Caddy does, the path is closed. The effect would be availability only; nothing is stored or disclosed.

**Claimed root cause.** deploy/compose.yaml starts gunicorn with its default worker class, three workers and --timeout 300 (raised from 30 for the nurse import, but applying to every request), and deploy/Caddyfile puts a bare reverse_proxy in front with no request_buffers, request_body limit or server read timeouts, so nothing in the repository completes or time-limits a request body before a one-request-at-a-time worker is committed to it.

### Source trace

1. **entrypoint** `deploy/Caddyfile:21` (`site block, reverse_proxy web:8000`) — Every request from outside except /metrics is proxied to gunicorn with default proxy settings; the file configures no body buffering, size limit or timeout.
2. **propagation** `deploy/compose.yaml:55` (`services.web.command`) — gunicorn config.wsgi with --workers 3 --timeout 300 and no worker class: three synchronous workers serve everything and a silent worker is ended only after 300 seconds.
3. **sink** `backend/accounts/api.py:104` (`login`) — The anonymous login route declares a JSON body parameter. The body is read to build it before the handler, including its CSRF check on line 107, runs; the local fixture showed the worker waiting here until the body arrived.

### Verified evidence

- `deploy/Caddyfile:16` — The site block holds only the TLS snippet import, the /metrics 404 and reverse_proxy web:8000; the file has no global options block, request_body or request_buffers.
- `deploy/compose.yaml:55` — The web command: gunicorn -c config/gunicorn.py --workers 3 --timeout 300, no -k or --worker-class. The fixture ran this command line with --workers 1 and a loopback bind.
- `deploy/compose.yaml:49` — The comment gives the reason for 300 seconds: one signed-in request, the 500-row nurse import. The flag applies to every request.
- `backend/config/gunicorn.py:5` — The gunicorn config file sets logging and a post_worker_init hook only; no worker_class, threads or timeouts.
- `backend/accounts/api.py:103` — POST /auth/login is registered with auth=None, so no session or role check comes before the body is read. In the installed django-ninja (read in the sandbox image; it is not in the repository), checks run first and body parameters second, so a route under SignedIn runs its sign-in check before its body parameter is built.
- `backend/accounts/api.py:107` — The login's CSRF check is the handler's first statement, after the body parameter has been built; in the fixture the 403 for a missing CSRF cookie came only once the body had arrived.

### Exact blockers

The repository does not contain it and the sandbox image has no Caddy, so it could not be observed and was not guessed.

### Bounded local plan
