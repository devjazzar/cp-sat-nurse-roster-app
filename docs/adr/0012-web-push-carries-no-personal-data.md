# Web Push through the browsers' push services: the payload names a kind and nothing else, and only the worker reaches the internet

Section 1 of the architecture left push notifications out of v1. The bell is read only by someone who opens the app, so a
swap to answer, a request window closing or a roster waiting for a decision is missed, and swaps expire. On 2026-11-07 the
user reversed that for Web Push alone: no email, no SMS, no service of ours and no third party beyond the push service each
browser already uses (Apple's, Google's, Mozilla's, Microsoft's). Three rules make that fit an installation whose promise is
that nothing about a nurse leaves the server.

1. **A push says which kind of thing waits, and nothing else.** Its payload is one kind code, from a fixed list, and the
   service worker holds the words ("You have a swap to answer") and the page a tap opens, with no month. No name, no date,
   no unit, no identifier of a swap or a roster crosses to the push service, encrypted or not. Only notifications with a
   deadline are pushed: a swap proposed (to the colleagues) or awaiting the manager, a request window opened, a window
   closed with requests waiting, a roster submitted (to the approvers) and a roster rejected. Everything else stays on the
   bell. The words are the same for everyone, so a push on a shared or lost device tells nothing.
2. **The worker sends, and the worker alone reaches the internet.** Every network an application service joins in
   `deploy/compose.yaml` is internal (only Caddy is on `public`); the worker joins one more, `egress`, that is not, and
   `web`, `db` and the solver stay as they were. The architecture's service table gains that one line with the spec, and
   ADR 0001's promise that the solver is unreachable from the internet holds, since its network is unchanged. A push is a queue job deferred inside the transaction that writes the notifications, so it commits
   or rolls back with them (ADR 0006), one job per `notify` call under the lock `push` (ADR 0009). Before sending, the job
   checks the thing still waits, and sends nothing for a swap already answered or a window since closed.
3. **The key pair is the installation's own, in the database.** Every push subscription is bound to the public key, so a
   key generated by `prepare` at first start and kept with the data comes back from a backup together with the devices it
   serves; a key in `.env` would die with the file. There is no scheduled rotation; a management command replaces the pair
   after a compromise, and each device re-subscribes on its next visit.

A subscription is held for one user, per device, turned on inside a tap on the Notifications page (iOS allows the question
nowhere else, and only from a web app on the Home Screen) and ended by turning it off, by Log out, by a deactivation, or by
the push service answering that the address is gone (404 or 410, at once) or failing ten sends in a row. The audit log
records the turning on and off by the user and nothing of the device; a drop is nobody's act and has no entry, as a swap's
expiry has none.

## Considered options

- **Email or SMS.** Each needs a provider's account and credentials, and would carry the words of the notification, with
  names and dates, to a third party. Still out of scope.
- **The payload encrypted and full.** Web Push encrypts every payload end to end, so the push service could not read a name;
  but the device's notification shade, its lock screen and its screenshots can, and nothing is gained by saying more than
  which page to open.
- **`web` sends at write time.** Simpler, but a push could leave before its transaction rolled back, and `web` would then
  need the internet, which nothing else it does calls for.
- **The key pair in `.env`** beside `SECRET_KEY`: one install step more, and a restore onto a fresh server with a new `.env`
  would silently end every device.

## Consequences

- Sections 1, 2, 7, 8 and 12 of the architecture change with the spec; the install guide names the push services' hosts the
  server must reach, and a hospital that blocks them loses pushes and nothing else.
- The service worker gains `push` and `notificationclick` listeners and still no `fetch` listener (ticket 23's rule holds);
  its test asserts that instead of the exact two listeners.
- The sending library (pywebpush, one maintainer) sits behind one module of ours, as Procrastinate does.
- A feature that adds a notification with a deadline adds its kind code and words; nothing else is per feature.
- A subscription also ends when the same user turns pushes on for an eleventh device, which ends their earliest turned on,
  with no entry, as any drop has none (ticket 67, from the security audit's lead 4). A renewal is not a new device.
